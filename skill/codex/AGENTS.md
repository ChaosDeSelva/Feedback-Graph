## Feedback Graph

The developer runs a Feedback Graph that learns from every time they pushed back on an agent's work (what was missed, why, and what context would have prevented it) and keeps a map of each project's code tied to those misses. Use its `feedback-graph` MCP tools in any project it tracks. If a tool says the directory is not a tracked project, carry on normally. If the server is unreachable, carry on and mention it once (the developer can start it with `docker compose up -d` in the Feedback Graph folder).

- **Before non-trivial work:** call `get_task_context` with `cwd`, a one or two sentence description of the task, and the `files` you expect to read or change. Treat approved lessons as project rules for this task; read similar past misses as what went wrong last time.
- **Before changing a file you do not know well:** call `get_module_context` with `cwd` and its `path`. Before changing a file other code depends on, call `impact` with `cwd` and the `paths`: check the dependents it lists and run the tests it names.
- **Before you say "done":** call `check_before_done` with `cwd`, the task, what you built and how you verified it, and `files_changed`. Address every gap it lists or say plainly why it does not apply; do not claim the work is finished while one is open.
- **When the developer pushes back:** fix the work first. Pushback they typed is picked up from this session on its own, so do not report it. Call `report_feedback` (with `cwd`, the feedback in their words, what you had built, and `session_id` if you know it) only when they ask you to record a miss (a post-mortem), or when a miss was not stated in words: they fixed or reverted your change themselves, or you found that earlier work in this session was wrong. It waits in the Feedback Graph Inbox for the developer; never confirm or approve anything there yourself.
