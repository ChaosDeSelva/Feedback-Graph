# Changelog

## 0.9.4 (2026-11-13)

- **An approve score on everything waiting for you.** Pending Inbox items, proposed lessons, proposed claims, questions the loop proposes to assign or close, and proposed loop decisions each carry a score from 0 to 10: the chance your verdict would be approve, with a one-line why of its top reasons (*8.6 · loop proposes approve_lesson: you kept 60 of 62 in its band (p .91)*, *2.0 · flagged risky-command; …*). It is read off the learning loop's existing calibration, not a new model: the Beta posterior of the proposing type in the call's confidence band (10 × *p*, or 10 × (1 − *p*) for a reject call), else the item's own uncalibrated signal (classifier confidence, lesson checks, extraction confidence) counted as 4 reviews; either way pulled toward 5 by the posterior's width, so little evidence reads as a judgement call. A lesson flagged *risky-command*, *may-hold-secret*, *off-turn* or *example-applies-when* scores at most 2; a claim with a flag or an open conflict at most 5. The scoring lives in one core module (`loop/approveScore.ts`).
- The Inbox, Lessons, Intake and Decisions pages show it as a chip on each row and in the detail (green 7 and up, red 3 and under, grey between; the why in the tooltip), offer sort by score, and *needs you* on Decisions lists the judgement calls first. The in-app Docs page and the guide's new **Approve score** section say how to read it and how it differs from the auto-apply bar (the bar reads the posterior's lower bound against τ; the score reads its shrunk estimate, so a 9 can still wait for you).
- API: `score` and `scoreWhy` on the list and detail answers of `/api/candidates`, `/api/lessons`, `/api/claims` and `/api/questions`; on decisions the field is `approveScore` (their `score` stays the loop's raw score). Those list routes and `/api/decisions` take `sort=score` (a paged list orders its first 500 matches; not with `after`). OpenAPI describes it.
- `fg inbox list`, `fg lessons list` and `fg decisions list` show a SCORE column and take `--sort score`; `fg inbox show` and `fg decisions show` print the why. The admin MCP list tools (`inbox_list`, `lessons_list`, `decisions_list`, `claims_list`, `questions_list`) carry `score` and `scoreWhy` on every row and take `sort: "score"`.

## 0.9.3 (2026-11-13)

- **Cloud sync works again for projects scanned since 0.9.0.** Scans and the docs reader were offered the kinds meant for what people said (`decision`, `plan`, `commitment`), and a cloud that does not know them refused the whole project (422, `facts.N.kind: Invalid enum value`). Scans and documents now use only the code kinds (a model that still answers a claim kind gets `architecture`), and a one-off repair at worker start re-kinds the scanned facts already stored that way as `architecture`, logged in Activity; facts from accepted claims keep their kinds.
- Sync never sends a fact kind the cloud does not take. A scanned fact goes under its nearest code kind; a claim's decision, plan or commitment, or an unknown kind, stays home and is counted (`skippedFacts` on the project's result, the run's Activity line, the worker log) while the rest of the project is sent. A cloud whose `/api/v1/sync-policy` lists `claimFactKinds` in `features` gets every kind as stored; if it still refuses a kind, the project is sent again with the kinds mapped.
- The sidebar's status items stay inside the sidebar at every width, collapsed included: the connections label truncates, collapsed its six dots go two to a row, and the health badge wraps to two lines with the whole status (its label too) in the tooltip.

## 0.9.1 (2026-11-12)

- **Inbox triage can apply on its own once earned.** `triage_inbox` moves from always-proposed to agent-facing (tier A): at bar 0.9, from 30 of your reviews in its confidence band, within the daily caps and the breaker. Your earlier reviews of its proposals count (the calibration is kept). It never confirms on its own an agent's report or an item from your own sessions, and never decides an item whose words read as a risky command or instructions to an agent: those stay proposals.
- **Decisions: "needs you".** The default view lists only what the learning loop could not decide, each with a one-line reason (always your call, not earned yet, under its bar, or the loop's own reason); the API sends it as `needsYou` on every proposed decision.
- **Renamed files keep their lessons.** The code map now keeps the renames git saw, and the learning loop's new housekeeping type `update_paths` moves a lesson's paths and trigger paths from a renamed file's old name to its new one (only when the old name is gone from the code map and the new one is in it), so the lesson keeps firing for that file. It is audited and rolled back on the Decisions page like any loop change.
- **Inbox dedupe by meaning.** A flagged turn and an agent's report are embedded when they arrive, and two of the same project within cosine 0.85 within 3 days are one Inbox item, as the same session or most of the same words within an hour already were: a reworded complaint, or the same one the next day, joins the first. With the embedding model down, matching is by words and session as before. Postgres migration 0063 adds the column.
- **Never merge, for good.** Rolling back a learning-loop merge of two lessons or claims records them as a pair you said are not the same, and `POST /api/distinct-pairs` records one directly; the loop never proposes merging that pair again, whatever the evidence (the old suppression lifted after 30 days or 1.5 times the evidence). Only you lift one (`DELETE /api/distinct-pairs`), never the operator token. Postgres migration 0063 adds the table.
- The Decisions page's merge decisions have a **Never merge** card: **Never merge these two** records the pair (`POST /api/distinct-pairs`), and the never-merge records naming either record are listed, each with **Lift** (`DELETE /api/distinct-pairs`, yours alone).
- **Near duplicates are judged, not measured.** Two lessons of one project with a cosine from 0.85 up to the duplicate flag (0.92), which the flag leaves alone, are compared first by their words and otherwise by the loop's model, yes or no, within its daily budget; yes or unsure proposes a merge for you, never applies one, and no is remembered so the pair is not asked again.
- **Similarity thresholds in one place**: `packages/core/src/thresholds.ts` holds the serve-by-meaning floor (0.78), the duplicate flag (0.92), the loop's auto-merge bar (0.95) and the Inbox dedupe (60% word overlap within 60 minutes), each with its unit and why it has its value; values unchanged. **`scripts/retrieval-eval.ts`** runs the labelled acme corpus through the local embedding model and the real serving path and reports precision and recall@k per task and overall; on `nomic-embed-text` the 0.78 floor kept every applying lesson (precision 0.67, recall 1.0 for what `search_graph` serves) while 0.80 lost two, so it stays ([operations](docs/operations.md#similarity-thresholds)).
- Settings' **Cloud sync** tab, with knowledge intake on, shows and sets whether the facts your accepted claims became are synced (`SYNC_CLAIMS`) and whether they name who said them (`SYNC_PEOPLE`), with what never goes either way. The choice is stored over `.env`'s, used by Sync now and the worker's schedule alike, and logged in Activity; `PUT /api/cloud/intake-sharing` sets it (operator verb `settings`).
- **Knowledge intake in export and import** (with `INTAKE_ENABLED`). `GET /api/export` adds `claims` (accepted ones, and those superseded by a conflict you settled; the quote only with `?quotes=1`), settled `conflicts` and the `people` who said them, by display name. A source's text, its questions, unreviewed claims and open conflicts are never exported, and a cloud sync never sends these sections. `POST /api/import` brings them back idempotently and with their statuses: people matched by name or added, claims under their ids (an accepted one files its fact again), settled conflicts made again where both sides are here; importing twice adds nothing. The Projects page's import summary counts them.
- **`fg ingest <file|->`** adds a source to knowledge intake from a terminal (`--project`, `--kind`, `--date`, `--participants`, `--title`, `--origin`, `--private` or `--shared`) through `POST /api/intake`. txt, md, vtt and srt are sent as they are; a pdf is turned into text with `pdftotext` and a docx, odt, rtf, html or epub with `pandoc` on your machine when installed (otherwise it says what to install); a binary file is refused, by its name or its first bytes. `--wait` follows the reading and lists the claims, open questions and conflicts drawn from it.
- **The learning loop helps with claims** (with `INTAKE_ENABLED`), through the same engine, gates, calibration, Decisions page and rollback as every loop type. Housekeeping: `link_claims` records that two claims from different sources say the same thing, and `merge_claims` folds a proposed duplicate into the claim it repeats, so you review it once; nothing agents see changes. `accept_claim` (agent-facing, bar 0.92) accepts a proposed fact or decision claim and files its fact as you would, only when its quote matched the source exactly, its statement adds nothing, its speaker is a person you confirmed, it is at least 80% sure, no conflict is open on it, and you accepted at least 70% of 20 or more claims of that type as written; never an opinion, never from notes an agent submitted. Always proposals: `propose_resolution` suggests B is true for a probable supersession, or not a conflict when the two sides no longer share a scope (approving it settles the conflict as your own choice would; choosing truth is never automatic), `assign_question` suggests who said the most about an open question, and `close_question` cites a later accepted claim that answers one. `PUT /api/loop/settings` now refuses `auto` for a type that is always a proposal, and the Settings page no longer offers it. Postgres migration 0063 adds the types.
- **Look-ups: "what do we know about X"** (with `INTAKE_ENABLED`). `GET /api/knowledge?q=` ranks the claims people made (who said each, when, from which call or notes), facts, approved lessons and open questions on a topic, grouped into decisions, plans and commitments, facts, opinions, lessons and questions, with `[disputed: <conflict>]` and both sides of every open conflict on them (`project`, `kinds`, `person`, `since`, `limit`; `format=md` for text). It is yours: it includes claims you have not accepted (marked unreviewed), opinions, quotes and open questions, and refuses the agent credential. Agents get the read-only MCP tool `what_do_we_know`, accepted knowledge only (no opinion, unreviewed claim, quote or question). Ask gains the starter *What do we know about …?*, and its answers cite accepted claims, open questions and an **Unresolved** section with both sides of each open conflict, presented as disputed. In a terminal: `fg know "<topic>"`, and `fg conflicts [--open]` / `fg conflicts show <id>`.

## 0.9.0 (2026-11-12)

- **Knowledge intake, opt-in with `INTAKE_ENABLED`** (off by default; `/api/status` reports it): give Feedback Graph what people said, a call transcript or notes, and the worker reads it into proposed **claims** (a fact, decision, plan, commitment or opinion, with who said it, when and the quote) and open **questions**, and checks them against what agents are already told for **conflicts** that you settle. Agents only ever see the claims you accept. A new **Intake** page in the Review group has Sources, Claims, Questions, Conflicts and People tabs. To turn it on, set `INTAKE_ENABLED=1` in `.env` and run `docker compose up -d`. Sources come in through **Add a source** on the Sources tab (paste or pick a file), `POST /api/intake`, the admin MCP tool `intake_submit` or an agent's `submit_notes`. See [docs/guide.md](docs/guide.md#intake) and [docs/operations.md](docs/operations.md#knowledge-intake).
- Sources: `POST /api/intake` takes pasted or uploaded text (txt, md, vtt, srt; up to 2,000,000 characters, answered 202 and stored in the background when large). Credentials and contact details (e-mail addresses, phone numbers, URL query tokens) are redacted before it is stored, and the original goes to the encrypted redaction archive unless `INTAKE_ARCHIVE=off`. A transcript is private by default. `GET /api/intake/sources`, `GET /api/intake/sources/:id` (text, utterances, claim spans), `POST …/:id/reread` and `DELETE …/:id?keep=facts|none`. All are owner-only, reads included; the operator token gets the new `intake` verb by default, and removing a source needs `docs_delete`.
- Intake text never reaches agents: the doc searches behind `get_task_context` (and its brief), `search_graph`, linked-project context and post-mortem context hunts leave intake sources out. Transcript text, quotes, questions and sources are never exported or synced.
- Extraction: the worker reads each source in windows of about 8,000 characters, one window a round, and resumes where it stopped after a restart. Speakers reach the model only as S1, S2, …; names spoken inside the text are not replaced. Every quote must be in the source and said by the speaker it names, or the claim is dropped. Lines that instruct an agent or hold a credential are dropped and counted in Activity, and a statement that adds numbers, dates or code names its quote lacks is flagged `statement-adds`. `INTAKE_LLM` (default `DOCS_LLM`, then `SCAN_LLM`, then the local model) is limited by `INTAKE_PROVIDER_ALLOW` (default `ollama,claude-cli`, so no company API key) and `INTAKE_LLM_CALLS_PER_DAY` (default 200). Its health shows on the Dashboard as "intake reader". The ordinary document reader never reads an intake source into facts.
- Review: accepting a claim that is not an opinion files it as a project fact (origin `claim`, which no code scan closes; facts gain the kinds `decision`, `plan` and `commitment`). An opinion stays attributed and is never given to agents unless you re-type it. Questions can be assigned, answered (your answer is an accepted claim) or dismissed; people renamed, given aliases, merged or forgotten. Writes need the new operator verb `claims_decide` (off by default); reads refuse the agent `API_TOKEN`.
- Contradiction detection: the worker compares each claim when its source is read or you accept it, each lesson you approve or edit, and (every `CONFLICT_SWEEP_MINUTES`, default 360, a capped page at a time) current facts, code facts included, and approved lessons, with their nearest neighbours that share a project (or a confirmed linked one) and a subject. Pairs whose numbers, dates, versions, negation or named choices differ, or that are very close, go to a judge that must quote both sides word for word; an answer that does not is dropped. A newer decision or plan by the same person, or by you, is recorded as a probable supersession for you to confirm; a contradiction inside one source becomes a question. Each judged pair is remembered, so an unchanged pair is never judged twice, and a pair you dismissed stays dismissed until either side changes. The judge is `CONFLICT_LLM` (default intake's model, held to `INTAKE_PROVIDER_ALLOW`), at most `CONFLICT_LLM_CALLS_PER_DAY` (default 60) calls a day.
- Conflicts tab: both sides side by side with what each says, who said it and when, the quote, the judge's explanation, the differences found, and whether agents see each now. Choose **A is true** or **B is true** (`1`, `2`: the other side is superseded, never deleted), **Both partly** (`3`, with a note, and optionally a reconciled statement filed as your fact that supersedes both) or **Not a conflict** (`4`, with a reason). Each choice is a `resolve_conflict` decision by you on the Decisions page; Undo rolls it back, which reopens the conflict and restores the loser exactly, and rolling back a learning-loop change it built on undoes the resolution first. Your decisions are never calibrated or counted as the loop's. `GET /api/conflicts`, `GET /api/conflicts/:id`, `POST /api/conflicts/:id/resolve`; the operator token needs the new verb `conflict_decide` (off by default).
- Disputed knowledge is served as disputed: while a conflict is open, the lessons and facts on either side carry `[disputed: <conflict id>]` in `get_task_context`, its brief and `search_graph`, and a **Disputed** section (inside the brief's budget) says what each side holds, who said it and when, and that neither is settled. A claim you have not accepted is named, never quoted. A gap `check_before_done` finds on a disputed lesson is listed under Cannot tell with the conflict. Once resolved, the loser is no longer served, and both partly is served with your note.
- MCP: `find_contradictions` (read-only, no model) checks a statement against the facts and approved lessons on its scope and lists what may contradict it and the open conflicts there; `submit_notes` hands you an agent's notes (up to 200 KB) as a private notes source marked `agent:<client>`, read into claims that wait for your review and are never accepted for you. The admin MCP endpoint gains `intake_submit`, `claims_list`, `claim_decide`, `questions_list`, `question_answer`, `conflicts_list` and `conflict_resolve`; each write is gated by its verb (`intake`, `claims_decide`, `conflict_decide`), and the lists need only the operator token.
- Cloud sync and export of claim facts: a fact with origin `claim` is never synced unless `SYNC_CLAIMS=true`. Even then its quote never goes, a fact from a private source (the default for transcripts and agent notes) never goes, and the speaker is named only with `SYNC_PEOPLE=true` (otherwise "a participant"). A claim fact that is superseded or deleted is withdrawn from the cloud on the next sync.
- Deleting a source keeps the facts its accepted claims became by default (`keep=facts`): its text, chunks, unaccepted claims and questions go, and so does its original in the redaction archive. `keep=none` also closes those facts, recorded as a `remove_source` decision by you on the Decisions page, which a rollback re-opens.
- Forgetting a person replaces their name with "former participant", deletes their aliases and unaccepted claims, and removes their name from the facts their accepted claims became and from earlier person Activity entries. The archived originals of sources they attended are not purged: they expire with the archive's retention, or delete the source to purge it.
- Storage on both Neo4j and Postgres (migration `0062_intake.sql`): sources, claims, questions, people and conflicts.
- `scripts/intake-eval.ts` scores intake and contradiction detection against a fictional fixture (`fixtures/intake`): claim and question precision and recall, planted-conflict recall, false conflicts per source, supersession accuracy, the judge's uncited rate, and the calls and seconds each phase took. It takes only local Ollama models or `claude-cli`: `--llm` runs the pipeline with one, and `--score` scores runs saved earlier without a model.
- A claim you accept is given to agents when a task is about it: its fact is filed as relevant to most changes (everyday) until you score it, and embedded from its statement alone (not the source it came from), so a task in its words reaches it. A conflict's reconciled statement likewise.
- Coming in 0.9.1, not in this release: look-ups (`what_do_we_know`, `GET /api/knowledge` and the Ask starter "What do we know about …?"), the learning loop's claim helpers (merging and linking claims, accepting claims, proposing a conflict resolution, assigning and closing questions; settling a conflict stays yours) and `fg ingest`.

## 0.8.3 (2026-11-12)

- Approved lessons are checked again each time a project's code map is rebuilt: one whose path or trigger glob no longer names anything in the repository, or a function it names that vanished or moved to another file, is flagged *its code changed* (`code-changed`) with what changed. It is never revoked for you, and the flag goes once the code is back or the lesson no longer names it. A path through a symlinked folder is no longer flagged *path not in repo*.
- **Lesson triggers are narrower.** An audit found one file served 7 unrelated lessons, one folder glob on 17 of 65 lessons and `**/*.sql` pulling lessons in wholesale. Triggers now come only from the lesson itself: its own paths, the file its comment was on, the files its fix edited and the code-shaped names its rule uses, never the files and code its post-mortem cited, the feedback's quotes, or (for a review comment on no file) the pull request's other files. A glob for a kind of file anywhere (`**/*.sql`, `**/migrations/**`, `*.sql`) is kept only when the rule says it of every such file, and is then flagged *trigger fires repo-wide* (`broad-trigger`) for you; the model's backfill may not propose one. `/**` goes only on a folder the repository has (a Dockerfile is itself, not `Dockerfile/**`), and an example in a rule (`e.g. ...`, a backticked phrase, a code block) is no trigger. On a task's words only a symbol shaped like code fires: a pattern or plain word the task shares with a lesson no longer serves it.
- At the first start, triggers worked out by the older rules are worked out again once, with no model, a batch a round (`lessons_checked` in Activity says how many lessons, and how many triggers before and after). Triggers you set are never touched. Expect most lessons to lose triggers: every pattern and every symbol the rule does not itself name (they came from the feedback and the cited code), and every folder glob of a file only the post-mortem cited. Postgres migration 0060 records which rules derived a lesson's triggers.
- `PATCH /api/lessons/:id` takes an optional `note` with a status or an edit: it is kept as the lesson's decision note and on its Activity entry, so an edit can say why (an edit without one keeps the last decision's note).

## 0.8.0 (2026-11-11)

0.8.0 adds the **learning loop**: the worker reads what happened to each lesson (served, judged, caught a gap, repeated, pushed back on) and your verdicts, and makes decisions about the graph, each one audited on a new **Decisions** page and reversible.

### Upgrading

- **The learning loop starts in `auto`.** Its mode is seeded once, at the first 0.8.0 start, from `LOOP_MODE`, else `auto`. On an install with `API_TOKEN` or `FG_OWNER_TOKEN` that means housekeeping (linking repeated misses, merging duplicate lessons, re-ranking lessons, retiring lessons that never help) applies on its own from the first round. Changes to what agents are told apply on their own only once your verdicts earn them: a type needs at least 20 of your verdicts on its proposals in the call's confidence band (one of 5, by its score) and that band's lower bound at τ or above, and then at most 5 such changes apply a day, 2 per project. That includes `approve_lesson` (τ 0.9), which **approves a proposed lesson without you**; until it has earned that, it only proposes. Every change is on the Decisions page, recorded as `loop:<v>`, and can be rolled back. To start more cautiously, put `LOOP_MODE=observe` (record what it would do, change nothing) or `LOOP_MODE=propose` (ask you about everything) in `.env` before the first `docker compose up` of 0.8.0; after that, Settings > Learning loop or `fg loop mode` sets it, and `LOOP_DISABLED=1` stops it.
- An install with neither token (or only blank ones) only observes. The worker learns whether the API has a token from the API itself, at each API start, so it observes until the API has started once (the API says *no token* until it listens and renews its answer every 30 s while its database answers; an answer older than 2 minutes reads as no token, so an API that failed at start never leaves an old *token* behind); a worker run outside Compose can be told with `FG_AUTH_CONFIGURED=1` (`1`, `true` or `yes`).
- **The first rounds catch up.** The loop reads the whole existing Activity log back to back, 500 entries a round (on a store of 50,000 entries, about 2 minutes on Postgres and 7 on Neo4j), then runs every 5 minutes, each round costing what changed since the last ([docs/operations.md](docs/operations.md)).
- Postgres migrations 0054 to 0059 run at the first start (decisions; lesson serving weights and each project's own similarity and fact-rank floors; the loop's facts and split lessons; its indexes at scale; the order of a decision's notes; C# namespaces kept with the code map). 0057 creates the `pg_trgm` extension, which ships with Postgres: on your own server the database user must be allowed to, as for `vector`. On Neo4j the first start links each stored decision to its targets, and then, in the background, each stored Activity entry, once (and removes the second link an earlier 0.8.0 build could leave): the api and the worker start without waiting for it, a target's entries are found meanwhile by reading the log, and a failed attempt is logged and tried again. Of the api and the worker starting together, one does this start-up work while the other waits.
- Lesson checks are version 10 and code maps version 6, so stored lessons are re-checked once and each code map is rebuilt once.

### The learning loop

- It runs in the worker, beside its other rounds and only when no post-mortem waits and no scan runs. It reads the Activity log into per-lesson outcome counts (served, the done check's verdicts, gaps fixed later in the same session, repeats while served or not, your pushback, edits and rejections) and your verdicts on its decisions into calibration per type and confidence band, then decides by mode (`off`, `observe`, `propose`, `auto`), tier and earned confidence. Every decision is logged as `loop:<v>` with its before and after, evidence, rationale, model and confidence. A round costs what changed since the last one, not the store's size: it judges the lessons the new entries name plus the next 500 of a slow sweep through all of them, and a round retried after a store error counts nothing twice.
- Tiers: housekeeping applies on its own under `auto`; agent-facing types apply on their own only once earned (above); `triage_inbox` and `tune_threshold` are always proposals. Only your own verdicts count toward what a type earns: approving and **Keep** raise it (as does leaving a change it applied on its own in place for 14 days while it is served, however long ago it was applied, or, for a lesson the change rejected, revoked or superseded, just left alone; one never served in 90 days gets no label and is not checked again), rejecting and rolling back lower it, and an operator token's verdicts never count. Before applying on its own the loop checks again that no target is one it never changes (written by you, demo data, a run's, one that may hold a secret or tells agents to run a risky command, a fact you wrote or whose relevance you set) and that you did not change it in the last 14 days; otherwise it proposes. Only a change that is actually applied takes one of the day's auto-apply slots.
- Decision types:
  - `link_misses` (housekeeping): links a new miss to an earlier one of the project it repeats (cosine ≥ 0.9 and a file both sessions edited, or the same cause).
  - `merge_duplicates` (housekeeping): a lesson flagged as a duplicate is superseded by the lesson it repeats, which takes the union of their paths; applied on its own only in one project when the duplicate is proposed, or when both are approved at cosine ≥ .95 with the duplicate's paths within the keeper's, else proposed.
  - `retire_lesson` (housekeeping): an approved lesson is revoked after 60 days, 15 servings and 8 verdicts with none catching a gap, at least 80% not applicable and no repeat of its miss; never one you wrote or touched within 30 days.
  - `rank_weight` (housekeeping): a lesson's serving weight moves ±0.1 within 0.5–1.5 from how its done-check verdicts went (5 decisive ones first). Each step is a new decision on the one before, also when it steps back to a weight it stepped from. It only breaks near-ties (within 0.02 of relevance) among lessons already tied to the named files, so no lesson reaches an agent that would not have, and the best match is never dropped. Verdicts that judged a lesson only through its trigger on other files count for neither it nor `retire_lesson`; a lesson whose own paths or miss's files cover a changed file is never trigger-only, wherever it ranked.
  - `reject_lesson` (agent-facing): rejects a proposal flagged platitude, generic, about feedback, not pushback, no miss, self-review or wrong session; one you edited is proposed at most.
  - `approve_lesson` (agent-facing, the highest bar, τ 0.9): approves a proposed lesson the lesson checks found nothing in, whose miss came from an Inbox item you confirmed, in a project where at least 60% of your own lesson decisions of the last 90 days (10 or more, an operator's left out) approved the lesson as written, with every path resolving to a mapped file, and whose miss repeats, or that a replay judge says would have flagged the diff your review comment was on. The replay judge (the loop's model) is asked only when no repeat stands, and never sees your feedback or the miss. A global lesson, one you touched in the last 14 days, or one whose miss came from a GitHub or Linear comment is proposed only. Rolling it back puts the lesson back to proposed, with its earlier decision time, decider and note.
  - `narrow_scope` (agent-facing): a global lesson judged and served in one project only becomes that project's, and a lesson with no paths gets the files edited to fix its miss.
  - `reword_lesson` (agent-facing): a model rewrite of a lesson flagged generic, two lessons in one, vague "applies when" or needs a path, or one served and repeated twice; a two-in-one lesson is split in two. The new text must pass the lesson checks and a judge must find it equivalent for the original miss; it may not add a URL, e-mail address, risky command, backticked code or a path the lesson and its miss's edited files do not have; the project's text is fenced as data in the prompts, which show your notes on earlier rewrites; at most 3 asked a round, none of a held-out lesson or one with a rewrite still proposed, and a refused rewrite is not asked again until the lesson's words change; rewording an approved lesson needs a bar .05 higher, and a lesson whose miss came from a GitHub or Linear comment is reworded only as a proposal. Its rationale reads as sentences, and a rewrite that only gives the lesson files says its words stay the same.
  - `record_fact` (agent-facing): a lesson flagged *looks like a fact* becomes a project fact of the loop's and the lesson is rejected (the same conversion as the Lessons page's **Convert to fact**); and a standing fact is proposed when you said the same thing about the code twice, in notes on loop decisions or in lessons you edited. The loop's facts have their own origin, `loop`: no scan closes, replaces or re-checks them, a model never rescores them, project fact counts list them apart, and task context labels them *learned from past feedback*, not as yours.
  - `triage_inbox` (always proposed): confirm a pending Inbox item the classifier is 85% sure is pushback or a correction; reject one a skip rule matches now, an agent's review of its own PR, or one under 35% with no agent report. The proposal expires when you decide the item yourself.
  - `tune_threshold` (always proposed): a project's own similarity and fact-rank floors within ±.03 of the defaults, from a replay of served facts against the files their sessions edited. `get_task_context` now records the scores of the facts it serves, the floors in force and what floors .03 lower would have added (a named file's own fact, served whatever the floors, is counted once, as served).
- Rollback restores each target exactly as it was. Later decisions that build on it, of any type, are undone with it, newest first, all or nothing, and a preview lists them and anything that blocks the rollback. When you changed a target since, the rollback (and its preview) is refused (409), the decision is marked *overridden*, and **Restore anyway** writes the old version over yours; a decision overridden before it was ever applied has nothing to restore. When another applied loop decision left the target so, the 409 names that decision and marks nothing, and a second click on a rollback already under way is refused the same way. A rolled-back call is not made again for 30 days unless its evidence grows by half. At start and before each round, a decision a crash left half applied is settled: a partial fact or split is undone and proposed again, a completed one keeps its decider and sync hold, and one still being applied is left to finish: a running apply renews its two-minute lease, so a slow embedding is never settled under it.
- A circuit breaker holds a type at *propose* until you set its mode again when you roll back two of its decisions in 7 days, or more than 20% of its last 10 applied (fewer than 5 applied count as 5, so three of three rolled back trip it). It counts rollbacks by when they were made, from when you last set the type's mode, so the rollbacks that tripped it do not trip it again, and a rollback counts once, against the decision you rolled back, not the later ones its cascade undid.
- A call the loop only observed is looked at again once its type proposes or applies (up to 500 a round, 5 for a type whose calls rest on a model's answer), so it is never stranded in *observed*. One that no longer holds is marked *expired*; one whose targets changed since is expired and the call made now takes its place. A call made again is recorded with the mode, score and confidence it is made with then, so an applied decision never reads *observed only*. A pause stops a call before it applies: a new one waits as a proposal, one already observed stays observed.
- Settings: `LOOP_MODE`, `LOOP_DISABLED`, `LOOP_LLM`, `LOOP_LLM_CALLS_PER_DAY` (40), `LOOP_AUTO_PER_DAY` (5), `LOOP_AUTO_PER_PROJECT` (2), `LOOP_SYNC_HOLD_DAYS` (7), `LOOP_HOLDOUT` (0.2) and `LOOP_TYPES`. The counts must be whole numbers and `LOOP_HOLDOUT` a plain decimal. `setup.sh` keeps `CODEX_AUTH_FILE` when `LOOP_LLM` is the only `codex-cli` job, and doctor's Codex-login hint checks every `codex-cli` job, `LOOP_LLM` included.
- A control group: `LOOP_HOLDOUT` of the lessons it could change, chosen by a fixed hash of their id, are never changed by it, and the Learning loop page compares them with the rest: repeat rate and how often they helped, with a 95% interval on the helpful rate.
- Measures of its value (`GET /api/loop/metrics`): the repeat rate per week, checks that caught a gap, gaps fixed per serving and the not-applicable share, each with a 95% interval; proposals per week; and the rollback rate per type, counted over every decision in the store. The Dashboard's **Learning-loop metrics** card shows the last four, beside the Quality card's repeat rate and checks that caught a gap.
- A lesson's track record shows why the loop believes what it does: servings, verdicts, gaps fixed, your pushback and edits, and its repeats (later misses at 0.9 similarity to its own, whether the lesson was served in that session or not), whether it is held out, and the timeline.
- Cloud sync hold: a lesson or fact the loop changed on its own is synced and exported as it was before (a global lesson `narrow_scope` moved, under the project it came from), until you **Keep** the decision or `LOOP_SYNC_HOLD_DAYS` pass without a rollback (also while its apply is still running). Your own edit, revoke or reject of it since is shared on the next sync and marks the decision *overridden*. The worker's lesson re-check leaves the paths of a lesson a loop decision stands on as they are.
- Decisions and notes are redacted before they are stored, and the redaction pass at worker start covers them too.
- It holds at scale on both stores: on 20,000 decisions a round with little new takes about a second, `GET /api/loop` and `GET /api/loop/metrics` count in the store with a fixed number of queries, exports read only the decisions still held, the Decisions list and its text search use indexes, and `approve_lesson` resolves paths against an index of the code map.
- `scripts/loop-replay.ts` replays the loop on history: it cuts a restored backup (or `--demo`, a synthetic public history) at a point in time, runs the loop in observe over the store as it was then, and reports per-type precision and recall against what you did afterwards, with a frozen held-out split reported apart. It refuses a store holding projects or lessons it did not write unless given `--wipe` (asked again on a terminal), refuses an install's bolt ports (7687, 7689 and `.env`'s `NEO4J_BOLT_PORT`), and checks every option before it connects. Without `--restore` or `--demo` it writes nothing to the store it reads, not even a schema upgrade, and refuses a Postgres store not at the current migrations.

### Lesson checks

- A new check, `risky-command` (chip *runs a risky command*): a lesson that tells agents to fetch a URL or run a command that downloads, installs, deletes, runs as root or decodes and runs something, or to read, print, copy or send secrets (SSH keys, `.env`, the environment, tokens, credentials, a keychain) to the PR, an issue, a chat, mail, a log or a URL, as an injected PR comment asks, is flagged for you, on new post-mortem lessons and stored ones, and the learning loop never targets it. It reads through fullwidth, lookalike, zero-width, bidi, %-escaped and defanged (`hxxps[:]//`) text and commands spelled out letter by letter (`c-u-r-l`), and knows package runners (`npx`, `dlx`, `uvx`, `bunx`), flags before an install's package, split `rm -r -f`, a bare domain to download and run, and inline code (`python -c`, `node -e`, `bash -c`, `powershell -enc`); a rule against doing so ("never print process.env") and `npm install` after changing package.json are not flagged. It knows only these shapes: a lesson in other words still reaches you as a proposal.
- A new check, `example-applies-when`, flags an "applies when" copied from an example lesson the post-mortem writer was shown when the miss (its rule, feedback, what was done and files) shares none of its words; the post-mortem prompt no longer quotes an example "applies when" to copy.

  Database, cache, config and map keys, identifiers, paths and versions are not ("The primary key is user_id2." stays).
- An uploaded image or document that shows a password no longer becomes a fact; uploaded text reaches a model fenced
  as data.
- No git command the tool runs on a project can run a filter, fsmonitor, textconv, external diff, signature program or
  hook the repository configures.
- An export with no project named covers the selected projects only.

### Scans, queues and scale
- **Scans take turns:** a big repository's sharded scan gives way after each shard to scans queued behind it, never
  gets its slot straight back while another waits, and picks up where it left off (its file list and plan kept while
  HEAD is unchanged).
- **Each queue says how it stands** (scans by project, classify, post-mortems, Ask answers): how many wait, the oldest
  wait, what runs now, in `/api/pipeline`, `fg status` and the Dashboard.
- **A GitHub sync past 1,000 pull requests** reads the rest over the next syncs instead of skipping them, and says so.
- **The Docs list** loads 100 at a time ("load older"; `limit` and `X-Next-Cursor` in the API).
- **Neo4j** has indexes for the per-project lookups the Projects page makes.
- **A post-mortem about auth code** no longer reads as "model not signed in"; one that keeps reading as unavailable is
  recorded as failed after five tries instead of holding the queue.

### Cloud sync
- A project that keeps failing backs off on its own; the others sync on their interval, and Settings names it.
- A project too large for the cloud is sent with its code map cut to the busiest files that fit, and says how many.
  The bundle says `codeFilesPartial`, so a cloud from 0.6.2 on keeps the files it left out of the team's code map.
- An unchanged project is not resent because rows came back in another order; Sync now and the scheduled sync no
  longer lose each other's record of what was sent.

### For testers and automation
- **Runs:** label requests with `x-fg-run: <id>` (or `?run=<id>` on `/mcp`, `fg --run <id>`); Activity shows and
  filters it. A run belongs to whoever opened it: a write under another caller's run id is refused.
- **`fg cleanup --run <id>`** removes only what that run wrote: a dry run first, `--apply` to do it, keeping anything
  you decided on since. The operator token may clean up only runs it opened.
- **Sandbox runs** (`x-fg-sandbox: 1`): their records reach only that run (every list, search, count, Ask pack and code
  map answer), and are never exported or synced.
- **`fg evidence <session>`** (`GET /api/sessions/:id/evidence`): what the tool saw in a session and what it decided.
- **`fg demo seed` / `fg demo remove`:** a labelled demo corpus in demo-shop so the lesson path can be tried on a fresh
  install. Running it is your approval of those demo lessons; it never touches a file a scan recorded.
- **Running Claude Code headless** (`claude -p`): a tool that is not allowed is denied, never prompted. Pass
  `--allowedTools "mcp__plugin_feedback-graph_fg" "Bash(git diff *)"`; with `scripts/install-agent.sh claude` instead
  of the plugin, allow `mcp__feedback-graph`. The plugin skill has the details.

### Safer by default
- **A lesson you edited or decided is never changed automatically:** a re-run post-mortem keeps your wording, the path
  clean-up leaves your paths, and a "no miss" finding only flags it. Automatic rejections never count as yours in the
  quality numbers or the writer's examples (operator-token decisions do, counted apart); ones already stored are
  corrected once at start.
- **A model outage, or a model busy with a scan, never uses up post-mortem attempts;** only an item that keeps failing
  while the model answers everything else is charged.
- **A run never takes over your records:** a sandbox tester's upload or link decision is its own copy beside yours,
  any other labelled run gets a 409 on your documents, links, pins, Inbox items, lessons and chats unless you opened
  it, and your decision on something a run made makes it yours, so cleanup leaves it. `fg cleanup` never labels its
  own request with the run it removes.
- **check_before_done judges only the lessons get_task_context would serve** (lessons tied to the changed files always),
  and when a diff is over its ~32 KB budget it keeps the files the lessons and misses name first. If you deny the tool,
  the Stop hook says so once and stops asking.

Sessions and Inbox candidates carry `source: 'claude' | 'codex'`. Agent CLIs are denied `/codex-sessions`.
- **Project candidates and selection API** for the Settings page: `GET /api/settings/projects` (every folder under the roots with its git remote, Claude Code and Codex session counts, last activity, selection, exclusion, alias and whether it has data; missing folders; a count of sessions outside every root), `PUT /api/settings/projects`, and `POST /api/settings/cleanup` (`{"confirm": "remove-unselected"}`) to delete the data of unselected projects. Writes are yours only, from the UI, and logged in Activity (**projects selected**, **unselected data removed**).
- **Projects are identified by their git remote,** not only by folder name. The worker reads each project's `origin` (only when the folder is itself a repo root), stores it normalized with credentials stripped (`github.com/org/repo`, `local/<name>`), and fills it in for existing projects on the next cycle without re-ingesting. A new folder holding a clone of a known remote is recorded under the existing project as an alias, logged in Activity as **project alias**; MCP calls from that folder resolve to the existing project. The Projects page shows the remote under each name, and the export bundle carries `projects: [{key, remote}]` (still `schemaVersion: 1`: the field is additive).

### Changed
- **One miss, one Inbox item.** When the detector flags pushback and an agent also reports it with `report_feedback` (within 60 minutes, same project, similar words or the same session), the two become one Inbox item that keeps both sources: candidates carry `origins` (`detector`, `agent`) and `agentReport`. A report made first is moved onto the transcript turn once the detector finds it, so its post-mortem sees the whole session. `report_feedback` takes an optional `session_id`. The skills now call `report_feedback` only for `/postmortem` and for misses the developer did not state in words, and no longer assume projects live under one folder. The Inbox shows such an item's report (**Reported by the agent**, and **and found by the detector** when both flagged it, with the agent's words and what it had done), and the worker's **candidate flagged** Activity entry links to the merged item. Postgres migration `0006_candidate_reports.sql`.
- **Feedback memories are imported as proposed lessons,** not approved ones: they wait in Lessons for your approval like a post-mortem's lesson, and are not served to agents until then. `MEMORY_AUTO_APPROVE=true` restores approving them on import. A memory lesson you have edited, approved or rejected is never changed by a later version of its file (as before); a proposed import has no decision time. Memory lessons imported before this change keep their status.
- **Post-mortems read AGENTS.md.** Besides CLAUDE.md (now in every parent folder up to the project root, not only the one above the repo) and Claude Code memory, a post-mortem reads AGENTS.md in the repo and its parents, labelled by source. For a Codex session AGENTS.md is what the agent had loaded and CLAUDE.md and memory are not; for Claude Code the reverse. Only a file the session's agent loads counts as available context. Context items gain the kind `agents_md` (Postgres migration `0005_agents_md.sql`).
- **You choose which project folders are read; nothing is read until you do.** The tool no longer ingests every project it finds. The selection is stored in the graph and gates ingest, memory import, scans, GitHub sync and MCP context. On upgrade, `INGEST_PROJECTS` seeds it (an install with `INGEST_PROJECTS=demo-shop` keeps reading exactly demo-shop); with it empty, nothing is selected, Activity logs it, `/api/status` carries `selection` and the header says **no projects selected**. From then on `INGEST_PROJECTS` is only that seed. `EXCLUDE_PROJECTS` remains a hard deny that the selection cannot override.
- `PROJECTS_DIR` now defaults to `~/code` in `docker-compose.yml` when it is not set, and `scripts/setup.sh` asks instead of assuming a folder. An existing `.env` that sets it is unaffected.
- Vulnerabilities are reported through GitHub private vulnerability reporting (SECURITY.md), with a first answer within 5 working days.
- New `NOTICE` listing the third-party fonts, tree-sitter grammars and libraries in the built UI and runtimes and their licenses; the images carry `LICENSE` and `NOTICE`. New [docs/editions.md](docs/editions.md) says what the open-source edition covers. The README opens with a public introduction and a quickstart from a fresh clone.
- **Upgrading keeps serving your lessons.** With `INGEST_PROJECTS` empty, the first start after upgrading selects the projects that already hold approved lessons, confirmed feedback, docs or scans (never an excluded one) instead of nothing, so MCP keeps serving what you approved; Activity lists them and says why. A new install still starts with nothing selected.
- **Global lessons reach every folder you have not excluded.** `get_task_context` and `check_before_done` in a folder under a root that is not selected now serve the global approved lessons (and nothing of the folder's own; reading its sessions stays opt-in). The "not a tracked project" answer now points to Settings.
- Changing `INGEST_PROJECTS` / `EXCLUDE_PROJECTS` no longer forgets every transcript cursor. Transcript cursors moved to a new table, so the first start after upgrading re-reads the selected projects' transcripts once (idempotent).

### Fixed
- **Selecting a second clone of a project you had not selected** no longer drops its sessions, marks them read, and leaves Settings unable to save. A clone follows its project: Settings shows it as a clone before anything of it is read, ticking it selects that project, and it is never made an alias of a project you have not selected. A folder saved before it became a clone or was excluded is dropped when you save (logged in Activity), never a reason to refuse the save.
- **Cleanup kept deleting data you selected:** memory lessons and docs filed under a selected project's clone folder are now kept.
- **A project cleaned up (or deleted while unselected) and selected again** has its whole history read again; before, only files that changed afterwards were.
- **Cleanup during a running ingest cycle** could have the cycle write the deleted project back. Each transcript is now written under a store-wide lock, against the selection as it is at that moment, and cleanup and project delete take the same lock.
- **Codex sessions that moved into a selected folder** after starting elsewhere were never read; they are now read for the turns in the selected folder, and counted in each folder they were in.
- **The first message after a Codex cwd switch** is now classified (it was skipped as if it opened the session).
- **Postgres: pgvector older than 0.8** made every vector search fail; startup now refuses it with the version found and how to upgrade. 0.8.0 is the documented minimum.
- **`reembed` after a crash** resumes where it stopped instead of re-embedding everything again (both stores).
- **A missing or unreachable model no longer uses up classification tries.** The classifier now tells a model it could not ask (connection refused, DNS, timeout, HTTP 5xx, model not found, not authorized or rate limited, CLI not installed or not signed in) from an answer it could not label. Only the second counts against a turn. When the model is unavailable, classification pauses for the cycle, the worker's last error reads `classifier unavailable: <reason>`, `/api/status` carries `models` (each job's model with `ok` and `reason`, post-mortem and scan included) and the sidebar badge says **classifier unavailable** (or **post-mortem model unavailable** / **scan model unavailable**) in its label. Turns given up on before this fix (or for any other reason) can be re-queued: the empty Inbox offers **Re-queue N turns that were given up**, owner-only (`POST /api/turns/requeue`), logged in Activity as **turns re-queued**; `/api/status` counts them (`givenUpTurns`). Postgres adds migration `0004_turns_requeued.sql` for the new Activity kind.
- **Post-mortems and scans no longer fail for a model that is down.** As for classification, a post-mortem whose model (or embedding model) could not be asked is not charged an attempt and the rest of the batch waits for the next cycle, and a scan goes back in the queue (its error says why) instead of failing, then runs once the model answers. The worker's last error reads `post-mortem model unavailable: <reason>`.
- With nothing selected, the empty Inbox and the MCP "not a tracked project" answer point to the Settings page.
- Postgres: text with NUL characters (seen in transcripts) failed to store; it is now stored without them, everywhere.
- The worker image installed whatever `@anthropic-ai/claude-code` and `@openai/codex` were newest at build time; they are pinned (Claude Code 2.1.309, for the confinement flags below, and Codex 0.162.0). `backups/` and the generated override are kept out of the Docker build context.
- `backup.sh` and `restore.sh` only knew Neo4j: on `STORE=postgres` they stopped the stack and dumped an empty Neo4j volume. They now read `STORE` from `.env`: on Postgres, `pg_dump -Fc` of the bundled service or of `DATABASE_URL` with nothing stopped, and a restore that replaces the schema in one transaction, with `state.tgz` and checksums as before. A backup records its store, a restore refuses the other store's backup, and a misconfigured `.env` is refused with a message.
- The per-project code map routes (`/api/projects/<key>/codemap/*`) answered for any project key; they now answer only for selected projects that are not in `EXCLUDE_PROJECTS`.
- `STORE=postgres` with the bundled service and an empty `POSTGRES_PASSWORD` failed later with an authentication error; startup now names `POSTGRES_PASSWORD`.
- The code map's repo check ran `git status` with optional locks on a read-only mount, and a `git status` that timed out made a dirty tree look clean. It now runs with `--no-optional-locks`, and a timeout is logged and rebuilds the map on the interval.
- Postgres: vector searches never used their HNSW indexes. They now can (the planner picks them for large projects), with iterative scans so a project's rows are still found when closer rows belong to other projects.
- Settings: a selected folder that later became another clone or was added to `EXCLUDE_PROJECTS` locked the page (it could not be unticked and every save failed). It can now be unticked, its row says why it is not read, and saving drops it. Zero counts, "never" and "not git" are now readable (WCAG AA contrast).
- Leaving Settings with an unsaved selection, or a lesson with unsaved edits (another page, lesson or tab, or closing the tab), now asks first instead of dropping the changes.
- Inbox: a quick `c` then `r` could send two decisions for the same item; one decision now runs at a time. The project filter lists every project and keeps showing the one picked when its list is empty. Errors in Inbox and Lessons clear on the next success, tab or item.
- Graph, Patterns, Activity and the Projects facts and docs cards no longer show a slow answer for a project or filter you have already left.
- The phone menu holds keyboard focus while open and returns it to the menu button when closed.
- The served UI logged a Content-Security-Policy error and fell back to a system font for one subset: the build inlined that font as a `data:` URL, which `default-src 'self'` refuses. Fonts are now always emitted as files, and `check.sh` fails if a build inlines one.
- `get_module_context` listed only the tests with a direct (or one-file) link to the file, so a file reached by tests through more imports showed none while `impact` listed them. It now lists the same tests `impact` does at its default depth (3 hops).
- The code map wrote a project's map beside a cleanup or project delete, so a project deleted while its map was being built could get its map back. The write now runs inside the same store-wide lock, after checking the project is still selected; the parse stays outside it.
- Files that left the code map stayed in the store as empty file entries for good. A new map now removes those nothing else refers to (never scanned, no facts, no session touches), on both backends.

### Security
- **Claude Code agents are confined to the repository.** `claude-cli` now runs with only Read, Grep and Glob, `--restricted` (file tools stay inside the project folder; the repository's own `.claude` settings are ignored) and `--permission-mode dontAsk`, and no longer pre-approves reads anywhere. Its deny rules for the worker's folders were relative paths that matched nothing (`Read(/proc/**)` means the project root's `proc`); they now use absolute paths (`Read(//proc/**)`), and the secret-file rules cover every path on disk too. Before this, a post-mortem agent could read other projects' `.env` files, every transcript, the state database, the Codex login and the worker's environment. The worker image pins Claude Code 2.1.309 for these flags.
- **`codex-cli` needs `ALLOW_UNCONFINED_CODEX=1`.** Codex's sandbox cannot be confined to the repository, so it can read everything the worker can (SECURITY.md lists it). A job set to `codex-cli` without the setting stops the worker at startup with a configuration error; a scan requested with Codex fails and says why.
- **`API_BIND` beyond loopback requires `API_TOKEN`.** Without a token the only guard was the Host header, which any client on the network can set; the API now refuses to start instead. Compose passes `API_BIND` to the api, and outside a container the server listens on `API_BIND` (127.0.0.1 by default) instead of every interface.
- Post-mortem and scan failure messages (which can quote model output) are redacted before they are stored, logged or served, on both backends.
- A `DATABASE_URL` password given as `?password=` is masked in logs and errors like one in the userinfo.

## 0.2.0 (2026-10-22)

Ready to run beyond a single laptop.

### Added
- **Access control.** `API_TOKEN` protects the API, MCP and UI (Bearer header or a sign-in page with an HttpOnly session cookie); `PUBLIC_HOSTS` and `API_BIND` for running behind a TLS proxy. Security headers on every response.
- **Operations.** `/api/ready` (fails while Neo4j is down), `/api/status` and a header badge with the worker's heartbeat, last cycle and last error; graceful shutdown that also stops running CLI agents; JSON access logs; container health checks; `scripts/setup.sh`, `backup.sh`, `restore.sh`, `check.sh`; CI workflow.
- **Validated configuration.** Every setting is checked at startup and all problems are reported at once, by name.
- **Data controls.** Export a project's lessons, misses, facts and docs as a versioned JSON bundle; delete everything learned from a project; `EXCLUDE_PROJECTS`; `TURN_RETENTION_DAYS`.
- **Embedding model safety.** The graph records which model embedded it; a changed `OLLAMA_EMBED_MODEL` is refused with a re-embed command (`pnpm reembed`).
- **UI.** Revoke an approved lesson, restore a rejected one, retry a post-mortem that gave up, see where each confirmed item's post-mortem stands, server error messages instead of status codes.
- Apache-2.0 license, SECURITY.md, CONTRIBUTING.md (DCO).

### Fixed
- Inbox shortcuts fired on Cmd+C / Ctrl+R; decisions could apply to an item other than the one shown after fast navigation (Inbox and Lessons).
- A whole-repo scan could leave a project with no facts after a failure part way; scanning with a different model did nothing on an unchanged repo and left near-duplicate facts.
- Fix commits were matched by comparing timestamps as text across time zones.
- Rejecting feedback you had confirmed still ran its post-mortem.
- The classifier retried unlabelable turns forever, and a hung model stalled a whole cycle.
- A CLI agent that ignored SIGTERM could hang the worker; its child processes held the pipes open.
- Codex could read secret files in the repository; Claude was missing several secret-file patterns; symlinks were followed.

- More than 30 PRs updated between GitHub syncs: the rest were skipped for good.
- Memory import covered only the first project root, ignored `INGEST_PROJECTS`, and stopped on a file deleted mid-read.
- Past misses and code facts reached agents without the untrusted-data fence; a doc title could start its own line.
- A mistyped project key or `cwd` with `..` created junk projects.
- Repeat scan requests queued duplicate scans; Linear search hits from other teams were stored as project docs; uploads with the same name replaced each other silently; document removals were not logged.
- An unreadable transcript was retried every 30 seconds; weekly stats counted session openers.
