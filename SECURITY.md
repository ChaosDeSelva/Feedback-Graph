# Security

Feedback Graph reads every Claude Code session transcript on your machine. This page says what it does with them, what leaves the machine, and where the limits are.

## Reporting a vulnerability

Report it privately through GitHub: open the [Security tab](https://github.com/ChaosDeSelva/Feedback-Graph/security) of https://github.com/ChaosDeSelva/Feedback-Graph and choose **Report a vulnerability** ([private vulnerability reporting](https://github.com/ChaosDeSelva/Feedback-Graph/security/advisories/new)). Include the version or commit, your setup (store, model providers) and steps to reproduce. Please do not open a public issue, pull request or discussion for a vulnerability.

You will get a first answer within 5 working days. Once the report is confirmed, we agree a disclosure date with you, normally within 90 days, and credit you in the advisory unless you prefer not to be named.

## What leaves your machine

Nothing, unless you configure it:

| Destination | When | What is sent |
|---|---|---|
| A model provider (OpenAI, Anthropic, OpenRouter, Groq, TypeSafe) | Only if you set that provider for a job | The redacted prompt for that job: the turn being classified, the post-mortem evidence, a file being scanned, or the work being checked |
| Claude / Codex via their CLIs | Only if you choose `claude-cli` / `codex-cli` (Codex also needs the codex-runner container, or `ALLOW_UNCONFINED_CODEX=1`) | The same prompts, plus whatever the agent reads while it explores read-only (see below for what each can reach) |
| GitHub | Only with `GITHUB_TOKEN` + `GITHUB_REPOS` | API reads of pull requests and comments |
| Linear | Only with `LINEAR_API_KEY` | A search query built from the feedback text |
| Feedback Graph Cloud (your team's org) | Only with `CLOUD_URL` + `CLOUD_TOKEN`, when you press Sync now or every `SYNC_INTERVAL_MINUTES` | Per selected project: key and git remote, approved lessons, plus the new status of any lesson the cloud already has (a rejected, superseded or deleted one, or one moved back to proposed, demotes or withdraws the team copy); a lesson you never approved only with `SYNC_SUGGESTIONS=true`, as a suggestion for an admin, misses without the quoted feedback or excerpts, current code facts, document titles and links, code map paths with hotspot numbers. Redacted again on the way out, over https only. Never transcripts, source, document text or embeddings |

The default setup uses Ollama on your own machine for everything, so nothing leaves it.

## Protections

- **Redaction.** Credentials are removed before anything is stored or sent to a model: API keys of the common providers, GitHub/GitLab/Slack/Hugging Face/npm/Linear tokens, JWTs, private keys, bearer tokens, passwords in URLs, `KEY=value` secrets, quoted config secrets, and any value whose key names a secret. Patterns live in `packages/core/src/redact.ts`; add yours there.
- **Secret files are never read.** `.env*`, `.mcp.json`, `.npmrc`, `.netrc`, `.pypirc`, `.git/config`, SSH keys, certificates and keystores, Terraform state and vars, and files named for secrets, credentials or passwords (`packages/core/src/secrets.ts`). The scanner skips them; Claude Code is denied them with `Read()` rules, inside the repository and anywhere else; Codex explores a copy of the repository that does not contain them. Symlinks are never followed.
- **Agents get least privilege.** CLI agents run read-only (no shell, edits or web), with an allowlisted environment: no other provider keys, no GitHub/Linear tokens, no database password. They run in their own process group and are killed on timeout or shutdown.
- **Claude Code is confined to the repository.** `claude-cli` runs with only the Read, Grep and Glob tools and `--restricted`, which keeps them inside the project folder it was started in and ignores that repository's own `.claude` settings, so a repository cannot grant itself more. Nothing outside the folder is pre-approved, and anything that would need approval is denied. On top of that, deny rules name the worker's own folders by absolute path (`/transcripts`, `/codex-sessions`, `/state`, `/codex`, `/proc`) and the secret files anywhere on disk. It cannot read other projects, the transcripts, the state database, the Codex login or any process environment.
- **Codex is confined by its container.** With `CODEX_RUNNER_URL` set, `codex-cli` runs in the codex-runner container (docs/operations.md), which has nothing else to read: Node, the Codex CLI, its own Codex home with your login file, and a scratch volume holding the copy of the repository for the current job (no secret files, one job at a time). No transcripts, projects, worker state or secrets in its environment, no published port, a read-only root filesystem, no capabilities and `no-new-privileges`. Codex runs read-only there too, so the commands it runs cannot write files (your Codex login included) or reach the network. The worker reaches the runner only with a random token the runner writes into the scratch volume at startup, and the runner refuses any folder outside that volume. A docker test (`codexRunner.docker.int.test.ts`) walks the runner's whole filesystem and every `/proc/*/environ` for a canary from a worker-only mount and a worker secret, and asks the real codex to read them.
- **External text is fenced.** PR comments, tickets, uploaded docs, past misses and code facts reach agents marked as data, not instructions, and cannot inject headings or code fences into the context.
- **You decide what is learned.** Flagged feedback waits for your confirmation; lessons are served only after you approve them. Decisions must come from the UI (a request without a browser Origin is refused), so an agent cannot approve its own lessons by accident.
- **The operator token is yours to hand out, and narrow.** With `FG_OPERATOR_TOKEN` set, an agent (or `./scripts/fg`) sending it as a Bearer may make the owner decisions `OPERATOR_ALLOW` names; by default not deciding lessons, choosing which project folders are read (`select_projects`), deleting data (a link between projects included: `links` confirms or dismisses one, `links_delete` removes it), importing, changing roots or integration keys, nor asking in Ask (`chat`, which spends your Claude or Codex subscription). `./scripts/setup.sh` makes the token only when you answer yes, and `--yes` answers yes for you: it then turns on `/mcp/admin` too, and says so. What it decides is recorded as `operator:<name>` on the item itself (an Inbox item's `decidedBy`, a fact's `relevanceBy`, an upload's `addedBy`) and in Activity, never as you. A note an agent leaves when it confirms an Inbox item reaches the post-mortem only as fenced, untrusted text, so it cannot steer the lesson. **The operator token also satisfies the read auth:** with `API_TOKEN` set it signs in for every `/api` and `/mcp` call just as `API_TOKEN` does, so it is a superset of it; keep it at least as private. A Bearer that matches neither token is refused with 401 and logged (method, path and agent name, never the token).
- **Agent input has limits.** The MCP tools' free-text arguments (task, query, summary, diff, feedback) have length caps, so a runaway client is refused before anything is embedded or stored.
- **Network exposure.** By default the API is published on 127.0.0.1 only and refuses other Host headers (DNS rebinding). A client that reaches the port can send any Host header, so the Host check is not access control: setting `API_BIND` to anything but a loopback address without `API_TOKEN` stops the API at startup with a configuration error. Cross-site and form-encoded writes are refused. Set `API_TOKEN` and `PUBLIC_HOSTS` to reach it from elsewhere: every API and MCP call then needs the token (Bearer header, or an HttpOnly, SameSite=Strict session cookie from the sign-in page), compared in constant time. Responses carry a strict Content-Security-Policy, `X-Frame-Options: DENY`, `nosniff` and `no-referrer`.
- **Team sync sends a fixed list of fields.** The sync bundle is rebuilt field by field from the export (`packages/core/src/cloud.ts`), so a field added to the store later does not leave until the sync is changed to send it. The cloud token is redacted from logs, errors and `/api/status`, is never passed to agent CLIs, and only goes to `CLOUD_URL` (redirects are refused; plain http only to a cloud on this machine: `localhost`, `127.0.0.1`, `[::1]` or `host.docker.internal`).
- **Containers** run as an unprivileged user, mount transcripts and projects read-only, and only mount the Codex login file (not all of `~/.codex`). The api and the worker drop every Linux capability (`cap_drop: [ALL]`) and run with `no-new-privileges`, so nothing in them can gain privileges, a setuid binary included.

## Known limits

- **Redaction is pattern based.** It catches credential formats, not customer names, personal data or proprietary code quoted in feedback. Do not point the tool at projects whose transcripts must never reach a hosted model; use `EXCLUDE_PROJECTS`, or keep every job on the local model.
- **The owner check is a guard, not a boundary.** Any process that can run as you can forge an Origin header, and could read `.env` and the database anyway. Likewise `OPERATOR_ALLOW` is a guard-rail for agents that use the operator token as intended, not a boundary against a local process: one that forges the browser's Origin passes every owner-only route and is logged as you.
- **`docker compose config` prints every secret in `.env`** (database passwords, `CLOUD_TOKEN`, API keys). Use `docker compose config --no-interpolate`, or redact the output, before pasting it into an issue.
- **Runner AppArmor default.** `CODEX_RUNNER_APPARMOR=unconfined` explicitly disables Docker's default AppArmor confinement for the runner on hosts without Ubuntu's user-namespace restriction. The supplied named Ubuntu profile is now enforced, allowing only runtime, temporary/job and runner scratch/login files, HTTPS/DNS sockets, local IPC, and the namespace/mount operations needed by bubblewrap. It does not use `flags=(unconfined)` or grant broad ptrace/raw-network access. Kernel namespace capability rules do not add Docker capabilities; the runner remains non-root with cap_drop ALL. These exceptions apply only to the runner. Its no-capabilities, no-new-privileges, read-only root and mandatory per-job mount/PID namespace remain separate controls. `/health` now tests the real nested sandbox and refuses readiness when it cannot start.
- **Procfs compatibility is an explicit operator choice.** Docker Desktop/OrbStack may require runner-only `systempaths=unconfined` to permit a new private `/proc` mount. That removes Docker's system-path masks in the runner and is not enabled by default. Never apply it to the worker/API, use privileged mode, or replace the job sandbox with an unconfined fallback. See docs/operations.md.
- **The codex-runner uses a deny-by-default seccomp allowlist.** `scripts/seccomp/codex-runner.json` derives from the pinned Apache-licensed Moby default, adding the namespace construction syscalls Bubblewrap/Codex need. It retains default denial of unrelated calls, explicitly excludes ptrace/process-memory access, BPF, kernel module loading, perf, keyrings and io_uring, and returns ENOSYS for clone3 so runtimes use classic clone. This exposes more namespace operations than Docker's stock filter, while narrowing the former `seccomp=unconfined` configuration. It does not enable the separate system-path exception. The runner still drops all Docker capabilities, runs non-root with no-new-privileges and a read-only root, and holds its Codex login and repository mirrors. Real outer/nested namespace and canary integration checks must pass before publishing a profile change.
- **`codex-cli` inside the worker is not confined, so it is off unless you accept that.** Without `CODEX_RUNNER_URL`, Codex's read-only sandbox can read the whole filesystem, and the worker has no way to narrow it to the repository: the worker cannot pass Codex per-path read rules the way it does for Claude Code, and Docker's default seccomp profile blocks the namespaces a wrapper like bubblewrap would need. Codex starts in a copy of the repository without secret files, but by absolute path it can read everything the worker can: every Claude Code and Codex transcript (`/transcripts`, `/codex-sessions`, including projects you did not select or excluded), every mounted project folder (`/roots/1`, `/roots/2`...) with its `.env` files, `/state` (the worker's database), the Codex login in `/codex`, and the worker's environment through `/proc` (database password, GitHub and Linear tokens, API keys). Its sandbox has no network, so it cannot send anything out directly, but a prompt injection in a transcript or repository could make it quote what it read into a lesson draft, a fact or an error, which are stored and shown to you. So without the runner, any job set to `codex-cli` (including a scan you start from the UI) refuses to run unless you set `ALLOW_UNCONFINED_CODEX=1`. Under Docker's default seccomp profile Codex's sandbox cannot start in the worker either, so the commands it runs there fail. Use the codex-runner container, `claude-cli` or an API provider.
- **Neo4j** listens on localhost ports 7476/7689 with the password from `.env`. Anyone who can reach those ports with the password has full access to the graph.
- **Transcript format.** Claude Code's JSONL format is undocumented and may change; parsing failures are logged and skipped, never guessed at.

- **Encrypted redaction originals contain secrets.** The API has only the encryption public key. Private keys live on the worker-only `redaction-key` volume, outside shared settings/project mounts. Ordinary state backups are owner-only and exclude decryption keys, which require a separate protected backup. Ciphertext expires after 30 days by default (configurable 1–365). The archive and key paths are scanner exclusions even when a repository ignores nothing. Existing v8 keys move out of the API-visible settings folder on upgrade; the API refuses archive startup until that migration has happened.


### Runner network boundary

The Codex runner joins an internal control network shared only with the worker, plus a separate egress bridge for model-provider HTTPS. It does not join the API/database bridge. The worker publishes timestamped sandbox readiness through the database; the API fails closed on missing or stale reports instead of connecting to the runner directly. Docker integration tests verify API DNS and direct container-IP access are blocked (including a forged Host header), while worker control access and provider-network HTTP still work. This boundary does not promise that every host-published service or external address is unreachable: keep API ports on loopback, configure authentication before publishing beyond it, and protect any intentionally exposed host gateway.


### Archive deletion and settings mounts

The key volume root and its private directory are mode 0700. A networkless, one-shot init container changes only that volume's ownership to HOST_UID/HOST_GID before the ordinary worker starts; it has no state or project mounts. The worker retires the v8 symmetric key when no retained v8 ciphertext remains, including after retention purges.

Encrypted envelopes carry only hashed lifecycle tags outside their ciphertext. Authorized project, document and run cleanup deletes matching originals and leaves other projects, other runs and kept records alone. Purge markers contain hashes, never original text, and expire with the archive retention window. The worker indexes earlier envelopes using its private key without renewing their original age. Historical batches whose original format omitted a sandbox or ownership identity are not reassigned by guesswork; any ambiguous original expires under its original retention deadline.

The API mounts only `state/api-settings` (roots, integration credentials and the run-key salt) and the encrypted archive directory. It no longer mounts all worker settings read-write. Setup migrates those three files without overwriting conflicting originals and refuses symlinked settings paths; keep the containers on the same checkout and rerun setup on upgrade.
