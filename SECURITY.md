# Security

Feedback Graph reads every Claude Code session transcript on your machine. This page says what it does with them, what leaves the machine, and where the limits are.

## Reporting a vulnerability

Report it privately through GitHub: open the [Security tab](https://github.com/ChaosDeSelva/Feedback-Graph/security) of https://github.com/ChaosDeSelva/Feedback-Graph and choose **Report a vulnerability** ([private vulnerability reporting](https://github.com/ChaosDeSelva/Feedback-Graph/security/advisories/new)). Include the version or commit, your setup (store, model providers) and steps to reproduce. Please do not open a public issue, pull request or discussion for a vulnerability.

You will get a first answer within 5 working days. Once the report is confirmed, we agree a disclosure date with you, normally within 90 days, and credit you in the advisory unless you prefer not to be named.

## What leaves your machine

Nothing, unless you configure it:

| Destination | When | What is sent |
|---|---|---|
| A model provider (OpenAI, Anthropic, OpenRouter, Groq, TypeSafe) | Only if you set that provider for a job | The redacted prompt for that job: the turn being classified, the post-mortem evidence, a file being scanned, the work being checked, an uploaded document being read, the turns of a session being summarized, an Ask question with the context and code it cites, or the learning loop's work: a lesson it would reword, and for the replay judge the original task, the agent's summary and the diff the feedback was about. With knowledge intake on, a window of a transcript or notes being read into claims, and two statements for the conflict judge; these go only to the providers in `INTAKE_PROVIDER_ALLOW` (Ollama and `claude-cli` by default) |
| Claude / Codex via their CLIs | Only if you choose `claude-cli` / `codex-cli` (Codex also needs the codex-runner container, or `ALLOW_UNCONFINED_CODEX=1`) | The same prompts, plus whatever the agent reads while it explores read-only (see below for what each can reach) |
| GitHub | Only with a GitHub token (`GITHUB_TOKEN`, or one saved in Settings, which wins), for selected projects with a github.com remote (or a `GITHUB_REPOS` entry) and pull request comments on | API reads of pull requests, their reviews and comments |
| Linear | Only with a Linear key (`LINEAR_API_KEY`, or one saved in Settings, which wins) | Reads of the issues and comments of the team each project maps to, and a search query built from the feedback text |
| Feedback Graph Cloud (your team's org) | Only with `CLOUD_URL` + `CLOUD_TOKEN`, when you press Sync now or every `SYNC_INTERVAL_MINUTES` | Per selected project: key and git remote, approved lessons, plus the new status of any lesson the cloud already has (a rejected, superseded or deleted one, or one moved back to proposed, demotes or withdraws the team copy); a lesson you never approved only with `SYNC_SUGGESTIONS=true`, as a suggestion for an admin, misses without the quoted feedback or excerpts, current code facts, document titles and links, code map paths with hotspot numbers; facts from accepted intake claims only with `SYNC_CLAIMS=true` (never their quotes, never from a private source, the speaker named only with `SYNC_PEOPLE=true`). Redacted again on the way out, over https only. Never session transcripts, intake sources (call transcripts and notes, their quotes and questions), source, document text or embeddings |

The default setup uses Ollama on your own machine for everything, so nothing leaves it.

## Protections

- **Redaction.** Credentials are removed before anything is stored or sent to a model (redaction rules v20; stored data is redacted again under new rules when the worker starts): API keys of the common providers, GitHub/GitLab/Slack/Hugging Face/npm/Linear tokens, JWTs, private keys, bearer tokens, passwords in URLs, `KEY=value` secrets and quoted config secrets. Rules read families rather than single forms: any HTTP header named for a credential (`X-Auth-Key`, `Fastly-Key`, `DD-APPLICATION-KEY`) and `Authorization` with any scheme, session cookies, a value given to a name ending in a credential word (`SMTP_PASS`, `storePassword`, `NEO4J_AUTH`, `APP_KEY`) in any syntax (env, YAML, JSON, XML, Gradle, subscripts, calls), the password arguments of the commands that take one (`cqlsh -p`, `sqlcmd -P`, `curl -u 'user:pass'`, `sqlplus user/pass@db`; `-p` stays for `ssh`, `docker run` or `psql`), PowerShell and Windows forms (`ConvertTo-SecureString -AsPlainText`, `cmdkey /pass:`, `schtasks /rp`, `net use`, unattend `<Password><Value>`), a token a few words after a credential word, and config forms such as redis `requirepass`, YAML anchors and keys nested under what they are for, Kubernetes/ECS `name`/`value` env pairs, SQL `ALTER ROLE … PASSWORD`/`IDENTIFIED BY`, Terraform variable defaults, Makefile `?=`, escaped JSON inside JSON, OpenVPN `<auth-user-pass>`, labelled recovery phrases, bare session cookies and Netscape cookie files. A value after a credential name is redacted whatever its length (an STS session token runs to 1,000+ characters). An unquoted value after a credential label (`password:`, `--token`, "the api key is") is redacted when it looks like a secret: letters mixed with digits or symbols, or a random-looking run of letters (16+, or 8+ after a password label); an identifier, type, call, path or ordinary word there is kept. A base64 key with a slash after a credential name is redacted even when it starts with `/` (one AWS secret access key in 64 does) once its letters and digits read as random; a path there is kept. Patterns live in `packages/core/src/redact.ts`; add yours there.
- **Secret files are never read.** `.env*`, `.mcp.json`, `.npmrc`, `.netrc`, `.pypirc`, `.git/config`, SSH keys, certificates and keystores, Terraform state and vars, CLI credential stores (ngrok v2's `~/.ngrok2/ngrok.yml`, Poetry's `auth.toml`, Helm's `repositories.yaml`, `kaggle.json`, the Hugging Face token, Copilot's `hosts.json`, `NuGet.Config`, `~/.aws/cli/cache`, sbt's `credentials.sbt`, Gemini CLI's `oauth_creds.json` and Vault's token included), browser cookie and login databases, WireGuard configs, KeePass files, data files (or files without an extension) named for secrets, credentials or passwords, such as `client_secret.json` or `aws/credentials`, `*.env` files in any folder (`config/prod.env`, `prod.env.sh`), and scripts named for the secrets themselves (`secrets.sh`, `.credentials.ps1`, `passwords.bat`), which export them; source such as `secrets.py` and scripts named for what they do (`rotate-secrets.sh`) are read (`packages/core/src/secrets.ts`). The scanner skips them; Claude Code is denied them with `Read()` rules, inside the repository and anywhere else; Codex explores a copy of the repository that does not contain them. Symlinks are never followed. `check_before_done` leaves out of a diff every file whose old or new path is a secret file, so renaming or deleting a `.env` does not show it, and counts the files it left out instead of naming them. Backups (`state.tgz`, database dumps) are secret files too.
- **Agents get least privilege.** CLI agents run read-only (no shell, edits or web), with an allowlisted environment: no other provider keys, no GitHub/Linear tokens, no database password. They run in their own process group and are killed on timeout or shutdown.
- **Claude Code is confined to the repository.** `claude-cli` runs with only the Read, Grep and Glob tools and `--restricted`, which keeps them inside the project folder it was started in and ignores that repository's own `.claude` settings, so a repository cannot grant itself more. Nothing outside the folder is pre-approved, and anything that would need approval is denied. On top of that, deny rules name the worker's own folders by absolute path (`/transcripts`, `/codex-sessions`, `/state`, `/redaction-key`, `/codex`, `/proc`) and the secret files anywhere on disk, in any case (`.ENV` on a case-insensitive filesystem is `.env`). It cannot read other projects, the transcripts, the state database, the Codex login or any process environment.
- **Codex is confined by its container.** With `CODEX_RUNNER_URL` set, `codex-cli` runs in the codex-runner container (docs/operations.md), which has nothing else to read: Node, the Codex CLI, its own Codex home with your login file, and a scratch volume holding the copy of the repository for the current job (no secret files, one job at a time). No transcripts, projects, worker state or secrets in its environment, no published port, a read-only root filesystem, no capabilities and `no-new-privileges`. Codex runs read-only there too, so the commands it runs cannot write files (your Codex login included) or reach the network. The worker reaches the runner only with a random token the runner writes into the scratch volume at startup, and the runner refuses any folder outside that volume. A docker test (`codexRunner.docker.int.test.ts`) walks the runner's whole filesystem and every `/proc/*/environ` for a canary from a worker-only mount and a worker secret, and asks the real codex to read them.
- **External text is fenced.** PR comments, tickets, uploaded docs, past misses and code facts reach agents marked as data, not instructions, and cannot inject headings or code fences into the context.
- **Injected instructions do not become lessons on their own.** A lesson that tells agents to fetch a URL or run a command that downloads, installs, runs a package, deletes, runs as root, runs inline code or decodes and runs something, or to read, print, copy or send secrets (SSH keys, `.env`, the environment, tokens, credentials, a keychain) to the pull request, an issue, a chat, mail, a log or a URL, is flagged *runs a risky command* for you, and the learning loop never approves, rewords or otherwise changes it. The check reads the text as a shell would (fullwidth forms folded, zero-width and bidi characters dropped, Cyrillic and Greek lookalikes as Latin, %-escapes decoded, `hxxp` and `[.]` restored, letters spelled out one by one as in `c-u-r-l` joined), but it knows only these shapes: a lesson in other words still reaches you as a proposal. The loop's rewrites (`reword_lesson`) are refused when they add a URL, e-mail address, such a command, backticked code or a path that neither the lesson nor the files its miss's session edited has, before the model judge is asked; and a rewrite or an approval of a lesson whose miss came from a GitHub or Linear comment is only ever proposed.
- **Call transcripts and notes (knowledge intake, off unless `INTAKE_ENABLED=1`).** What people said in a call is sensitive and names people who did not agree to be recorded. Before a source is stored or any model sees it, credentials and contact details (e-mail addresses, phone numbers, URL query tokens) are redacted, and speakers reach the model only as S1, S2, ... A transcript, and an agent's notes, are private by default: their claim facts are never synced, even with `SYNC_CLAIMS=true`. The text, quotes, questions and sources are never served to agents, exported or synced; agents get only the claims you accept, as facts. The original text is kept in the encrypted redaction archive like other redacted input, unless `INTAKE_ARCHIVE=off` keeps it nowhere; deleting a source purges its original. Forgetting a person removes their name and deletes their unaccepted claims. Details: docs/operations.md, *Knowledge intake*.
- **Agent-submitted notes are untrusted input.** `submit_notes` (MCP, not read-only) takes at most 200 KB and stores it as a private notes source marked `agent:<client>`. Its text is fenced as data in every prompt, statements that instruct an agent or hold a credential are dropped (counted in Activity), and every quote must occur in the notes, said by the speaker it names. Its claims are only ever proposed: nothing from it reaches agents until you accept it, and nothing accepts it for you.
- **You decide what is learned, or let your verdicts earn the learning loop that right.** Flagged feedback waits for your confirmation, and lessons are served only once approved. You approve them: the signed-in UI, or `FG_OWNER_TOKEN` with `X-FG-Owner: true`. The one exception is the learning loop in `auto` mode, **the default**: its `approve_lesson` decision may approve a proposed lesson on its own once your own verdicts on its proposals have earned it, counted per type and confidence band: at least 20 of them in the call's band, with that band's lower bound at or above τ 0.9, at most 5 agent-facing changes a day and 2 per project. Until then it only proposes. Each such approval is a decision on the Decisions page, recorded as `loop:<v>`, and can be rolled back. To keep every approval yours, set the loop to `propose` (Settings > Learning loop, or `fg loop mode propose`), or `LOOP_MODE=propose` in `.env` before its first start. The API token agents hold cannot decide lessons or teach the loop, and the operator token cannot decide lessons unless `OPERATOR_ALLOW` names `lesson_decide`, nor decide on the loop's decisions without `loop_decide`; an operator's verdicts never count toward what the loop earns, so an agent cannot approve its own lessons or vote the loop into approving them.
- **Credentials have separate powers.** `API_TOKEN` authenticates reads and MCP tools. It cannot sign a browser in, and as a Bearer it never gets owner authority, even with forged `Origin`, Fetch Metadata or `X-FG-Owner` headers. `FG_OWNER_TOKEN` is the owner's credential: it signs a browser in, and as a Bearer it works on an owner route only with `X-FG-Owner: true`. Setup and `install-agent.sh` never give it to agents. `./scripts/fg signin` trades it, at localhost only, for a one-time browser sign-in link: a random code the API keeps only as a hash in memory. It works once, for 60 s, only at `localhost`, `127.0.0.1` or `[::1]`, is refused through a proxy (and spent by that attempt), and is never logged. With `FG_OPERATOR_TOKEN` set, an agent (or `./scripts/fg`) may make only the owner decisions `OPERATOR_ALLOW` names; by default not deciding lessons, choosing project folders, deleting data, importing, changing settings/integration keys, asking in Ask, or deciding on or configuring the learning loop (`loop_decide`, `loop_settings`). Operator writes are recorded as `operator:<name>`, never as you. The operator token also satisfies read auth, so keep it at least as private as `API_TOKEN`. A Bearer matching none of these is refused and never logged.
- **Owner sessions can be revoked.** A browser session is a random cookie (HttpOnly, SameSite=Strict, 30 days) named for the port it was issued on (`fg_session_<port>`), so two installs on one machine never share one and the name reveals nothing about a credential. Signing out saves the revocation to `owner-session-revocations.json` in the api's settings folder before it is honoured; if that save fails, the sign-out fails. A missing or corrupt revocation file refuses every earlier session (sign in again) and is rewritten, so deleting it cannot revive a signed-out cookie. A restore signs every owner session out.
- **Agent input has limits.** The MCP tools' free-text arguments (task, query, summary, diff, feedback) have length caps, so a runaway client is refused before anything is embedded or stored.
- **Network exposure.** By default the API is published on 127.0.0.1 only and refuses other Host headers (DNS rebinding). A client that reaches the port can send any Host header, so the Host check is not access control. Without `API_TOKEN`, reads are answered only to a socket peer on this machine (loopback, or one of the API's own networks, which is how Docker's published port arrives), never by `Host`, and setting `API_BIND` to anything but a loopback address without `API_TOKEN` stops the API at startup with a configuration error. Cross-site and form-encoded writes are refused. Set `API_TOKEN` and `PUBLIC_HOSTS` to reach it from elsewhere: every API and MCP call then needs a credential (`API_TOKEN` or the operator token as a Bearer, or the owner's session cookie), compared in constant time. Responses carry a strict Content-Security-Policy, `X-Frame-Options: DENY`, `nosniff` and `no-referrer`.
- **Team sync sends a fixed list of fields.** The sync bundle is rebuilt field by field from the export (`packages/core/src/cloud.ts`), so a field added to the store later does not leave until the sync is changed to send it. The cloud token is redacted from logs, errors and `/api/status`, is never passed to agent CLIs, and only goes to `CLOUD_URL` (redirects are refused; plain http only to a cloud on this machine: `localhost`, `127.0.0.1`, `[::1]` or `host.docker.internal`).
- **Containers** run as an unprivileged user, mount transcripts and projects read-only, and only mount the Codex login file (not all of `~/.codex`). The api and the worker drop every Linux capability (`cap_drop: [ALL]`) and run with `no-new-privileges`, so nothing in them can gain privileges, a setuid binary included.

## Known limits

- **Redaction is pattern based.** It catches credential formats, not customer names, personal data or proprietary code quoted in feedback. Knowledge intake also redacts contact details, but names spoken inside a transcript ("ask Ana about it") cannot be found reliably and reach the intake model as they are, which is why its default model is local. A few formats are indistinguishable from ordinary values without context: a Mailchimp key (`<32 hex>-us6`) has the shape of an md5 hash with a region suffix, and no case, datacenter or entropy test separates them, so it is redacted only when Mailchimp is named on its line (before it, only with a key word or a label: `mailchimp api key`, `Mailchimp:`, `MAILCHIMP_KEY=`), a credential label or the `apikey` Authorization scheme precedes it, or it is curl's `-u`/`--user` password. A bare key pasted with none of those is kept. A labelled value made only of letters is told from a long identifier by how English its letter pairs are and, in mixed case, how its case changes. Measured on 100,000 random values per length after `password:`, the share kept is about 1 in 400 lowercase, 1 in 380 uppercase and 1 in 200 mixed case at 16 letters; 1 in 1500, 1 in 1800 and 1 in 530 at 20; and 1 in 6000, 1 in 5000 and 1 in 1500 at 24. None of 6,500 dictionary words of 16+ letters is redacted. After a password label (`password:`, `--pass`, `DB_PASS=`) a letter-only value of 8-15 letters is read the same way, with more misses: about 1 in 10 random ones of 8 letters is kept, 1 in 30 of 10, 1 in 60 of 12 (1 in 45 in mixed case) and 1 in 110 of 14 (1 in 70 in mixed case), while about 1 in 1200 dictionary words and 1 in 200 identifiers of that length is redacted. A shorter one, or one after any other label, is kept. Measured for redaction v18 on two invented sets of credential forms (seeded fakes in 19 families; the second was written after the rules and scored once): 288/288 and 44/44 caught, against 105/288 and 20/44 under v17, with 1 of 119 nearby benign lines changed under both. On every tracked line of two real repositories (about 2.8 million lines) v18 redacts 5 lines v17 did not, each a literal password assigned in SQL or a Makefile, and stops redacting 2 that are not secrets. Do not point the tool at projects whose transcripts must never reach a hosted model; use `EXCLUDE_PROJECTS`, or keep every job on the local model.
- **A tokenless install is read-only for owner actions and readable by anything on this machine.** Behind Docker's published port the API cannot tell your browser from another program, so owner actions are refused until `./scripts/setup.sh --yes --enable-auth`. Reads are answered to any peer on this machine, including other containers on the same Docker host (OrbStack and Docker Desktop route them through the gateway). Fetch Metadata stops web pages, CSRF and DNS rebinding, but a local process can forge the browser headers. Setup therefore recommends and creates `API_TOKEN`; only authentication is a boundary. The learning loop on such an install only observes, since nobody could roll its changes back: the worker reads that from the API's own answer (`state/api-settings/auth-state.json`), so a blank token counts as none on both sides. The API writes *no token* there first at each start and its real answer only once it listens, renewed every 30 s while its database answers, so an API that fails at start, stops or loses its database leaves the loop observing within 2 minutes. A process that can read this install's `.env` can also obtain its secrets, so protect that file. `OPERATOR_ALLOW` remains a guard-rail for a deliberately issued operator token, while `FG_OWNER_TOKEN` is the distinct headless-owner credential.
- **`docker compose config` prints every secret in `.env`** (database passwords, `CLOUD_TOKEN`, API keys). Use `docker compose config --no-interpolate`, or redact the output, before pasting it into an issue.
- **Runner AppArmor default.** `CODEX_RUNNER_APPARMOR=unconfined` explicitly disables Docker's default AppArmor confinement for the runner on hosts without Ubuntu's user-namespace restriction. The supplied Ubuntu profile (`CODEX_RUNNER_APPARMOR=feedback-graph-codex-runner`) is enforced, allowing only runtime, temporary/job and runner scratch/login files, HTTPS/DNS sockets, local IPC, and the namespace/mount operations needed by bubblewrap. It does not use `flags=(unconfined)` or grant broad ptrace/raw-network access. Kernel namespace capability rules do not add Docker capabilities; the runner remains non-root with cap_drop ALL. These exceptions apply only to the runner. Its no-capabilities, no-new-privileges, read-only root and mandatory per-job mount/PID namespace remain separate controls. `/health` tests the real nested sandbox and refuses readiness when it cannot start.
- **Procfs compatibility is an explicit operator choice.** Docker Desktop/OrbStack may require runner-only `systempaths=unconfined` to permit a new private `/proc` mount. That removes Docker's system-path masks in the runner and is not enabled by default. Never apply it to the worker/API, use privileged mode, or replace the job sandbox with an unconfined fallback. See docs/operations.md.
- **The codex-runner uses a deny-by-default seccomp allowlist.** `scripts/seccomp/codex-runner.json` derives from the pinned Apache-licensed Moby default, adding the namespace construction syscalls Bubblewrap/Codex need. It retains default denial of unrelated calls, explicitly excludes ptrace/process-memory access, BPF, kernel module loading, perf, keyrings and io_uring, and returns ENOSYS for clone3 so runtimes use classic clone. This exposes more namespace operations than Docker's stock filter, while narrowing the former `seccomp=unconfined` configuration. It does not enable the separate system-path exception. The runner still drops all Docker capabilities, runs non-root with no-new-privileges and a read-only root, and holds its Codex login and repository mirrors. Real outer/nested namespace and canary integration checks must pass before publishing a profile change.
- **`codex-cli` inside the worker is not confined, so it is off unless you accept that.** Without `CODEX_RUNNER_URL`, Codex's read-only sandbox can read the whole filesystem, and the worker has no way to narrow it to the repository: the worker cannot pass Codex per-path read rules the way it does for Claude Code, and Docker's default seccomp profile blocks the namespaces a wrapper like bubblewrap would need. Codex starts in a copy of the repository without secret files, but by absolute path it can read everything the worker can: every Claude Code and Codex transcript (`/transcripts`, `/codex-sessions`, including projects you did not select or excluded), every mounted project folder (`/roots/1`, `/roots/2`...) with its `.env` files, `/state` (the worker's database), the Codex login in `/codex`, and the worker's environment through `/proc` (database password, GitHub and Linear tokens, API keys). Its sandbox has no network, so it cannot send anything out directly, but a prompt injection in a transcript or repository could make it quote what it read into a lesson draft, a fact or an error, which are stored and shown to you. So without the runner, any job set to `codex-cli` (including a scan you start from the UI) refuses to run unless you set `ALLOW_UNCONFINED_CODEX=1`. Under Docker's default seccomp profile Codex's sandbox cannot start in the worker either, so the commands it runs there fail. Use the codex-runner container, `claude-cli` or an API provider.
- **Neo4j** listens on localhost ports 7476/7689 with the password from `.env`. Anyone who can reach those ports with the password has full access to the graph.
- **Transcript format.** Claude Code's JSONL format is undocumented and may change; parsing failures are logged and skipped, never guessed at.
- **Encrypted redaction originals contain secrets.** The API has only the encryption public key. Private keys live on the worker-only `redaction-key` volume, outside shared settings/project mounts. Ordinary state backups are owner-only and exclude decryption keys, which require a separate protected backup. Ciphertext expires after 30 days by default (`REDACTION_ARCHIVE_RETENTION_DAYS`, 1–365). The archive and key paths are scanner exclusions even when a repository ignores nothing. Existing v8 keys move out of the API-visible settings folder on upgrade; the API refuses archive startup until that migration has happened.

### Runner network boundary

The Codex runner joins an internal control network shared only with the worker, plus a separate egress bridge for model-provider HTTPS. It does not join the API/database bridge. The worker publishes timestamped sandbox readiness through the database; the API fails closed on missing or stale reports instead of connecting to the runner directly. Docker integration tests verify API DNS and direct container-IP access are blocked (including a forged Host header), while worker control access and provider-network HTTP still work. This boundary does not promise that every host-published service or external address is unreachable: keep API ports on loopback, configure authentication before publishing beyond it, and protect any intentionally exposed host gateway.

### Archive deletion and settings mounts

The key volume root and its private directory are mode 0700. A networkless, one-shot init container changes only that volume's ownership to HOST_UID/HOST_GID before the ordinary worker starts; it has no state or project mounts. The worker retires the v8 symmetric key when no retained v8 ciphertext remains, including after retention purges.

Encrypted envelopes carry only hashed lifecycle tags outside their ciphertext. Authorized project, document and run cleanup deletes matching originals and leaves other projects, other runs and kept records alone. Purge markers contain hashes, never original text, and expire with the archive retention window. The worker indexes earlier envelopes using its private key without renewing their original age. Historical batches whose original format omitted a sandbox or ownership identity are not reassigned by guesswork; any ambiguous original expires under its original retention deadline.

The API mounts only `state/api-settings` (roots, integration credentials, the run-key salt and the owner-session revocations) and the encrypted archive directory, not the worker's settings. Setup moves the roots, integrations and salt files there from `state/settings` only while creating `state/api-settings` (an install from before it), so a file the worker leaves in `state/settings` later is never taken for a setting, and refuses symlinked settings paths; keep the containers on the same checkout and rerun setup on upgrade. The host scripts treat everything under `./state` as the worker's to change: setup, doctor, backup, restore and `fg` never write, read, chmod or remove a path there through a link (a file is written in `.host/`, which no container can write (the worker mounts only its two empty `--no-transcripts` folders there, read-only), and hard-linked into place; one is read only as a plain file, a few KiB at most), refuse a link where a mounted folder or file belongs, and backups leave out anything there that is not a file or folder. The worker mounts each `./state` path another container mounts a second time, so it cannot replace one with a link for Docker to follow at the next start; `state/api-settings` it mounts read-only, since the project roots saved there decide the host folders setup mounts (it only reads `integrations.json` there). No other bind-mount source may be under `./state`: setup refuses a transcripts folder, Codex login file or project folder there (`--no-transcripts` keeps its empty folders in `.host/`, and moves those an older setup left in `state/`), since the worker could swap it for a link to any host folder before a restart.

### Restores

`restore.sh` checks a backup before it stops anything. It refuses a `state.tgz` that holds links or paths outside `state/`, unpacks past `FG_RESTORE_MAX_STATE_MB` (default 8192, counted from the gzip stream, so a gzip bomb stops there) or holds more than `FG_RESTORE_MAX_STATE_FILES` (default 200,000) entries, and a backup larger than the free space it unpacks or loads into. It writes the sign-out cut-off and the runner-disabled flag as new files, never through what the archive holds, and carries the runner flag over only from a plain file. Restore, backup and doctor refuse a restore journal with an unexpected key or value instead of acting on it. `backup.sh` and `restore.sh` refuse to stop, dump or load containers that another folder started under this install's name.
