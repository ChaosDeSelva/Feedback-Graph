# Judge queue estimates

`check_before_done` returns judge queue telemetry in MCP `structuredContent.queue` and explains it in the text response. It includes capacity, live running/waiting counts, the request's current waiting position (1 is next), checks ahead on arrival, whether the request still holds a slot, the position a new retry would currently take, and a retry delay when appropriate.

Estimates cover judge admission and service, not embedding, store access or the entire task. `estimate.startMs` and `completionMs` are millisecond windows measured from the response snapshot. `estimate.scope` is `judge`. `state` is `waiting`, `running`, `completed`, or `retry_required`.

The queue keeps up to 64 actual service durations. A duration ends only when a running call really releases its slot, including when its caller already timed out. Queued requests cancelled before running contribute no duration and are removed immediately. With observations, the lower/upper service scenarios use the 25th/90th percentiles and simulate FIFO service across the configured concurrency, subtracting the elapsed time of active calls. These are estimates, not confidence intervals or guaranteed deadlines. Recent model speed and future demand can differ.

At cold start, `estimate.source` is `response_budget` and `samples` is zero. The window uses zero to the configured response budget per service wave; this is an explicitly labeled scheduling scenario, not evidence that a model will release a slot by that time. Once actual calls finish, `source` becomes `observed`. When an active call exceeds the observed service range, its lane is unavailable in the upper scenario. `overdue` becomes true only after its own response deadline. Healthy or free lanes still provide a finite scheduling estimate; the upper endpoint is `null` only when no such lane can serve the request. An uncooperative call continues occupying real capacity. The `running` notification is emitted when a call starts; its window is measured at that admission snapshot, not a later progress update.

A check still obeys its end-to-end response deadline. A timed-out request has `retained: false`, `position: null`, and `state: retry_required`. It is not a background check and holds no physical queue slot. Authenticated callers can retain retry priority as described below. `nextRetryPosition` and the estimate describe where that retry would enter the live queue at that moment; `retryAfterMs` is a bounded pacing suggestion derived from the estimated next start, not a reservation or promise. A retry starts with a fresh response budget. A queued or not-judged answer is not a completed check, so the Stop hook continues to block completion.

The response also gives a median-service scenario alongside the wider interval when observations are available. Completed checks show measured waiting and service durations rather than a meaningless 0–0 second ETA. An unusually slow but still-in-budget call does not produce the warning for a call past its response deadline. Retries start a new request with a fresh response budget. When an authenticated check times out before its judge starts, the server retains its original queue ordinal for two minutes. A matching retry joins ahead of newer waiting checks, without reserving capacity while absent. `retryPriority` reports whether priority is retained, restored, and its remaining lifetime. The text response reports this separately from the physical queue position.

Priority is bound to the validated caller credential/capability, run, project, session, task, changed files, actual diff and selected lessons. Different callers or changed checks cannot reuse it. Unauthenticated requests have no retained priority. Repeated timeouts do not extend the original expiry; concurrent duplicates cannot take the same reservation. The process keeps at most 1,024 reservations, evicts the oldest when full, and loses reservations on restart. Expiry, eviction or restart simply returns the retry to ordinary FIFO order. Running calls receive cancellation on timeout and are never restarted by this mechanism; no model work runs for an absent retry, and no results are shared.
