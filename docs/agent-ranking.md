# Agent relevance scores

Agent context (`get_task_context`, `search_graph`, `check_before_done`) shows one number per miss, fact and document: its raw embedding similarity, clamped to 0–1 and shown to two decimals (`match 0.82`). It is not a probability that the item applies. A miss tied to a file the task names says *on a file you named* instead; it is structural evidence, with no invented similarity.

Behind that number each item also has a weighted rank, which decides what is served:

- **Two floors.** With the standard semantic embedder, a miss, fact or document chunk must reach 0.78 raw similarity and a 0.80 weighted rank, in the project and in linked projects alike. The 0.80 threshold comes from the 0.6.8 field report; it is not a universal embedding calibration. An embedder calibrated below 0.78 keeps its configured floor for both instead of the cosine-only threshold.
- **Facts** are weighted by similarity, the fact's everyday relevance and how close it is to the named files and services. A fact on a file the task names keeps its raw-floor match even when the weighting puts it below 0.80; this does not extend to sibling or unrelated files.
- **Misses** are weighted by how close the paths they mention are to the named files. A miss is served (by `get_task_context`, its linked projects and Ask) or judged (by `check_before_done`) only when it shares a file with the work (the same file, or one in the folder the miss names or names a file in) or is at least `MISS_MIN_SIMILARITY` similar to it (default 0.85, the bar a lesson learned elsewhere clears on similarity alone). In the 0.7.6 value sweep every miss served at 0.80–0.82 was unrelated, and every one judged came back not applicable. An embedder calibrated below the default floor uses its own floor as that bar unless one is set.
- **Documents** are weighted by the paths they mention, like misses.

Ask's prompt shows the weighted rank to three decimals (`rank 0.801`), so a value just below 0.80 cannot look like an accepted 0.80. Ask also puts exact named paths and file-name matches before token-ranked siblings, and includes those files' symbols within its hit budget, so a known file is not called absent because its symbol names differ from the question.

`get_task_context` and `check_before_done` do not pick lessons by similarity (`search_graph` lists them with a `relevance`). They serve lessons by file ties and, since 0.7.6, by their lesson triggers (path globs on the named or changed files; patterns and symbols on the lines a diff adds or the task's words). A trigger is not a score, so a lesson served by one says *why served: trigger …* instead.

A task naming its own PR leaves that PR's lessons, misses and documents out of its context, and the answer names the PRs left out. Structural file evidence from other PRs and sessions stays. Only an explicit PR identity in the task or an explicitly named commit counts, never the checkout's unrelated HEAD, and text such as "PR 1 of 2" is not a PR identity.

## What the learning loop may change

- **Lesson serving weight** (`rank_weight`, 0.5–1.5, ±0.1 per decision, from the Wilson bounds of a lesson's pre-done verdicts on its own files once it has 5 decisive ones; a verdict from a check that judged the lesson only because its trigger fired on other files does not count). The weight only breaks near-ties: weighted lessons are reordered among themselves by score plus their weight's share of 0.02, so a weight never moves a lesson past one more than 0.02 more relevant, and a lesson with no weight (every held-out lesson among them) keeps its place. Code-map lessons the search did not find are ordered the same way among themselves, and the cut keeps the first six. The weight acts only on lessons already tied to the named files in the project: it never serves a lesson that would not have been served, and `check_before_done` judges the same order.
- **A project's own floors** (`tune_threshold`, always your call): the .78 raw-similarity and .80 weighted-rank floors for that project's misses, facts and documents, within ±.03 of the defaults. `get_task_context` records each served fact's similarity and rank, the floors in force, and the facts floors .03 lower would have added; the loop replays these against the files each session went on to edit and proposes a move only where the facts it adds or drops are measurably more or less precise than what is served now.
